# Agent Event Stream

## 目标

把 Codex Web 的反馈模型从“最终结果 + 局部报错”升级为“Agent 运行轨迹流”。

用户在对话里发出一次请求后，Agent 的所有关键行为都应该进入同一条对话流：开始工作、连接模型、状态变化、重试、工具调用、工具输出、网络错误、模型错误、最终失败、最终完成。用户不应该等到一分钟后才看到一句最终失败，也不应该被一个脱离对话的全局错误浮窗打断。

## 理想状态

一次 Agent turn 应该像一条可观察的时间线。

用户能实时看到 Agent 当前处在什么状态：正在思考、正在请求模型、正在调用工具、正在重试、已经失败、失败原因是什么。普通状态保持轻量，错误状态清晰可辨，详细信息可以展开查看。

错误、重试、工具调用都属于这轮 Agent 输出的一部分。因此它们应该和这轮消息一起出现，也应该在用户回退这轮时一起消失。刷新页面后，界面应从事件历史里恢复同样的轨迹，而不是依赖额外的前端错误缓存。

## 第一性原则

事实先于包装。后端和 Agent 已经产生的事件，不应该被前端吞掉、猜测、简化成一句模糊文案，或者藏在开发者看不到的地方。

上下文决定归属。一次请求里的状态和错误属于这次 turn，而不是属于整个应用的全局弹窗。全局诊断可以存在，但不能替代对话流。

显示不是解释。前端可以做轻量分类和视觉层级，比如 status、retry、tool、error，但不能依赖特定字符串去猜某个错误是否重要。未知事件也应该有可见表达。

细节默认可达。用户首先看到简短、可扫读的状态或错误摘要；需要排障时，可以展开查看原始 payload、错误 code、URL、HTTP status、stack、details。

回退是时间线操作。用户回退某个 turn，就是回退这轮 Agent 的输出过程。该 turn 的状态、重试、错误、工具事件都应该随之消失。

## 不要过度防御性编程

不要为了“避免刷屏”去重错误或合并重复事件。重试五次就是五次事件。

不要预设用户看不懂错误。Codex Web 面向的是会排查问题的用户，隐藏细节会破坏工具价值。

不要用大而全的错误系统绕开现有事件流。优先把真实事件接入对话流，而不是另造 localStorage 错误收集器、toast 队列或右下角浮窗。

不要为了兼容未知情况写一堆沉默 fallback。未知事件可以以通用事件块显示原始内容。

不要把 UI 做成客服产品。这里需要的是工程工具的可观察性，而不是“友好但空洞”的报错提示。

## 高层方案

前端消息模型增加 Agent event 表达，用于承载 status、retry、tool、network、model、error 等事件。它们作为 assistant message 的一部分渲染，按事件发生顺序进入当前 turn。

实时 WebSocket 事件和历史 `/api/events` 事件应走同一套转换逻辑，保证刷新前后看到的轨迹一致。

后端 bridge 层应尽量透传 Codex app-server 的事件细节。如果 retry 或中间状态目前没有被前端收到，应优先查清事件源是否存在；存在就透传，不存在再考虑在 bridge 层补充结构化状态事件。

错误展示采用两层结构：默认显示一行明确摘要，展开后显示完整 details。摘要用于快速判断发生了什么，details 用于真实排障。

全局诊断入口可以作为后续补充，但只能是辅助视图，不能默认覆盖主对话，也不能成为错误显示的主路径。

## 非目标

不做右下角运行期错误浮窗。

不做基于特定 retry 文案的前端正则识别。

不做错误去重。

不把错误从 turn 里抽离成独立生命周期。

不在第一版里追求复杂日志检索、过滤、导出或长期持久化。
